# 物品与战斗修改设计

状态：用户已于 2026-11-11 确认设计并要求开始实现。本文不代表功能已经实现或运行验收。

## 目标与已确认决策

在现有 SafeDialogueTools 的“修改作弊”页开放“物品”“战斗”，继续参考旧内置修改 DLL 的功能和数据定位，但不复用其危险的资源加载、物品实例复用和战斗结算实现。

用户已确认：

- 物品支持名称及描述搜索、分类筛选、原生图标、名称/品质/说明/拥有数量、指定数量添加及移除；包含普通物品和装备。
- 战斗支持当前我方单人或全队恢复，以及击败全部敌人；不提供直接发奖按钮。
- 任务类物品和信件只能浏览，不允许添加或移除；不提供强制绕过。
- 删除装备只作用于背包里明确选定的具体实例，排除已穿戴及标记“锁定熔解”的实例。
- 本次打开面板后的第一次物品增删前必须成功创建检查点；本次连续增删复用该检查点。关闭面板或读档后重新建立，建立失败则拒绝修改。
- 战斗操作要求已有且完整校验通过的战前检查点，显示其时间与地点；没有则禁用，不在战斗中强制保存。
- 击败敌人需二次确认，执行期间禁止重复提交。
- 游戏原生图标必须正常；不能再以插件自建 AssetBundle 加载器抢占游戏资源。性能和存档可靠性优先。

## 现状与证据

- `Core/CheatPanel.cs` 中物品、战斗、世界仍未开放；本次仅开放前两类。
- 现有面板由 `RuntimeDriver` 的 IMGUI 绘制，已有输入隔断、分辨率缩放、页签与分类；保留这些行为。
- `Plugin.TogglePanel()` 当前禁止在战斗中打开面板，物品/属性等编辑又统一使用禁止战斗的 `CheatEditor.EditBlockReason()`。必须将“面板能否展示”“普通写入能否执行”“战斗操作能否执行”分开，不能全局撤掉战斗限制。
- `CheatSessionState.TryBeginPreEditCheckpoint()` 当前在写检查点前标记成功；`EnsurePreEditCheckpoint()` 失败后只返回警告，调用方仍继续。新物品流程不能据此认定已有保护。新建独立、成功后才提交的物品会话保护状态，避免把旧标记当作成功证明；本次不批量改变既有属性/点数操作行为。
- `CheckpointStore.Validate()` 校验版本指纹、文件集合和 SHA-256；`NativeSave.Validate()` 校验原生存档结构。仅显示存档库摘要不能替代这两次校验。
- `tools/tmp/linghsu_decoded/Y1/YTP.cs` 使用游戏数据表及 `PlayerDataManager.AddItemToBag/AddEquipToBag/RemoveBagItem` 等接口，可用于定位。装备添加时必须独立创建实例，不能照搬旧代码重复提交同一个实例/列表。
- `_EquipType == EquipType.任务` 与 `_ItemType == ItemType.信` 可明确识别保护对象。数据表未提供能可靠识别所有剧情/唯一物品的通用标记；“非任务类”不能等同于“绝无剧情关联”。
- 原生图标链：`FormatRenderer` 图标 URL → `MyGLoader` / `MyGloaderManager.LoadIcon` → `Main.m_Resource.LoadAB` → 原生 `NTexture` 池。`MyGLoader.FreeExternal` 与原生借用引用配对释放。
- 旧 `Y1.Mde` 直接 `AssetBundle.LoadFromFile`，并全局拦截该方法。用户已指出这种实现导致同 Bundle 重复加载及游戏自身物品缺图；新代码不得引入这条路径或相关补丁。
- 原生 `BattleUnitData.SkillCure(1f)` 只恢复气血、护甲、真气，不清异常、不复活，且气血恢复可能被“滞息”阻挡。
- 旧 `SkillCure(-1f)` 不能作为击败敌人的实现：可能不扣气血、使护甲和真气变负，且自身不触发死亡/结算。
- 原生 `BattleManager.EnemyHurt(...)`、`DieEnemy(...)`、`EnemyDies(...)` 构成需进一步核实的死亡处理链；`EnemyDies` 内部调用奖励。禁止插件直接调用 `DieAward()` 或自行叠加发奖。

## 实现方案比较与选择

1. **延续 IMGUI 面板，借用原生图标加载器（采用）。** 改动集中，延续现有输入与布局，原生加载器负责 Bundle 和纹理生命周期；插件只负责可见范围、有限借用和绘制。需要验证原生纹理的 UV/旋转、引用配对及 IL2CPP 包装的生命周期。
2. **整页改用 FairyGUI。** 原生 UI 融合较好，但需重建布局、事件和焦点处理，扩大存读档与战斗输入回归范围。本次不选。
3. **插件独立读 Bundle、导出全套图片或接管游戏加载。** 与原生资源一致性和用户明确约束冲突，不采用。

这是在用户已确定功能、并将实现细节交由开发者处理的前提下作出的工程选择。

## 用户界面

沿用现有深色面板和缩放，不重做现有角色、点数、其他页。

物品页的结构：

```text
物品    [名称 / 描述搜索]    [分类]    [全部 / 仅背包]
------------------------------------------------------
可滚动结果列表                    选中物品详情
[原生图标] 名称 / 品质 / 拥有数     [原生图标] 名称 / 品质
[原生图标] 名称 / 品质 / 拥有数     描述、类别、拥有数量
...                              数量 [ 1 ]  [添加] [移除]
                                 装备移除：具体实例及保护状态
------------------------------------------------------
修改前检查点：时间 / 地点 / 已验证，或明确禁用原因
```

- 搜索匹配名称和描述；分类包含全部、装备、道具、材料、秘籍、任务、战斗、图纸、灵化道具、山海录。任务与信件仍能展示图标和详情。
- `仅背包` 是便利筛选（工程默认），不扩大可修改范围；普通物品拥有数量为背包数量，装备显示同型号在背包内的实例数量，不把穿戴数量混作可删数量。
- 装备移除必须展开/选择具体实例，显示足以区分它的名称、实例标识、品质及词条等已能从原生数据读出的信息。若无法稳定区分两个实例，则禁用该组删除，不猜测。
- 物品数量为正整数。数值溢出、超过拥有数量、未知类型、模板不完整或背包容量条件不明时拒绝，不静默截断或换成别的目标。
- 默认一次普通物品上限 999、装备添加上限 10（工程初始限制，可根据原生接口和验收结果收紧）。若超过原生堆叠/容量限制，以更小的合法边界为准。
- 原生加载失败时显示中性占位与“图片暂不可用”；不能借机换用独立 Bundle 加载。失败不会让数量/目标错位。

战斗页的结构：

```text
战斗    当前阶段 / 暂不可用原因
战前检查点：时间、地点、等级（点击操作时再次完整校验）
------------------------------------------------------
我方角色 [下拉选择]    [恢复气血 / 护甲 / 真气]
                      [恢复我方全队]
------------------------------------------------------
[击败全部敌人] → 确认对话框 → 执行中 / 结果
```

- 操作是手动单次按钮，不是自动无敌、持续回血或伤害倍率开关。
- 恢复只包含仍有效、存活、已确认属于我方的参战单位；不复活，不清异常，不修改永久基础属性。若“滞息”使气血未恢复，结果准确说明，不显示“全满”假成功。
- 击败按钮只保证走经过验证的当前战斗原生死亡处理，不替游戏改写本场特殊目标、援军波次或剧情胜负条件。界面说明“处理当前敌方，胜负由游戏判定”；无法证明适配的特殊战斗禁用该按钮。
- 确认框显示当前敌方数量和回退检查点时间；确认时重新解析当前战斗与敌方快照，发生变化则取消本次确认。
- 战斗中其他作弊写入、F5/F6 仍遵循原有限制。检查点是恢复保障，不表示允许战斗中即时读档撤销；发生异常后，需回到游戏允许完整读档的状态，必要时退出重进再恢复。

## 模块与数据职责

- **Core 纯逻辑**：物品种类与稳定键、搜索和分类索引、数值与保护策略、装备实例删除选择、物品会话保护状态、战斗阶段与单次执行状态、确认失效逻辑。不得依赖 Unity 或调用游戏。
- **Plugin 物品适配器**：一次生成只读目录，读取背包快照，通过已验证原生方法增删；不直接修改背包容器。提交前重新解析数据和具体实例。
- **Plugin 图标借用层**：通过原生 `MyGLoader` 持有 URL/纹理，优先由原生 `Dispose` / `FreeExternal` 归还引用；不自行制造 Sprite 或复制 Texture2D。具体 IL2CPP 可用构造方式由实现阶段核实。
- **Plugin 战斗适配器**：解析当前参战单位和阶段，驱动被验证的原生恢复/死亡处理；面板只发起请求，不直接操纵气血或发奖。
- **面板**：只读快照渲染、虚拟列表、输入草稿、禁用原因及结果；不在 `OnGUI` 中做资源加载、目录全量枚举、检查点校验/写入或游戏修改。
- **测试桥**：只在既有隔离测试模式下扩展检查命令与诊断结果，不在正式环境暴露新远程入口。

## 图标生命周期与效率

1. 用稳定的 `(物品/装备种类, 数据ID)` 建目录键。原生图标 URL 视为不透明标识，原样交给游戏管理器；不擅自对 JSON/资源名统一转小写。插件不得维护第二份 Bundle 所有权。
2. 目录元数据首次进入物品页时按帧构建；只在数据表/存档/版本发生变化时重建。不得为了建立目录而加载全套图片或为所有装备生成持久实例。
3. 搜索结果只在查询/类别/目录版本变化时计算并缓存；输入采用约 100 ms 合并（工程初始值），不能每次 `OnGUI` 全量 LINQ 扫描或重新分配结果。
4. 列表只绘制可见行及少量预取行。图片请求在 `Update` 主线程队列执行，初始每帧最多 2 个新请求；单帧经过约 2 ms 后不再开始下一项。原生调用可能同步阻塞，预算无法抢占单次慢调用，因此必须实测冷加载尾延迟，不能宣称完全异步。
5. 原生加载器借用池初始最多 64 个图标，淘汰不可见且非详情使用的项；不持有无界缓存。面板关闭、切出物品页、场景/读档世代变化、插件销毁时及时归还租借。
6. 优先让 `MyGLoader` 原生生命周期配对取得和释放引用。若这条封装在 IL2CPP 中不可安全使用，必须先证明替代引用路径和失败清理等价，再改变方案；不能默认手动 `ReleaseRef` 等价。
7. 每个请求附带面板/目录世代号；过期结果不绑定新行，并归还原生引用。清理与回调都在 Unity 主线程处理。
8. 使用原生纹理及有效 UV 范围绘制；覆盖图集、旋转和可能独立 alpha 的情况。无法正确呈现时须补齐绘制支持或标记该类暂不可显示，不能拉伸整张图集假装完成。
9. 不修改或释放游戏所有的 Bundle、纹理和原生池；插件自制的背景纹理仍按原有机制销毁。

## 物品写入与检查点会话

会话从打开面板开始，关闭面板、读档开始、返回标题、转场/战斗切入、玩家存档实例变化或异常时结束。切换面板内部页签不新建会话；重复打开必须重新取得保护。

每次增删的顺序固定：

1. 解析当前输入和稳定目标键，检查版本指纹、普通编辑安全状态、任务/信保护、数量与具体实例资格。
2. 未保护时创建完整原生检查点；`Create` 成功后，再经 `Store.Validate` 与 `NativeSave.Validate` 才能把本会话标为受保护。配置未启用、授权不满足、磁盘/校验失败均拒绝写入；失败状态允许用户排除原因后重试。
3. 展示并保留该 generation 作为回退目标。有效会话复用它，但每次提交仍检查目标文件存在；真正提交前完整校验，不能在绘制循环反复算哈希。
4. 检查点创建可能跨越时间，创建后必须重新验证游戏状态、背包快照及目标身份；失效则取消操作，不能继续用旧引用。
5. 添加普通物品走验证过的原生添加接口；每件装备单独从模板生成独立实例和词条/ID。移除普通物品不超过当前数量；装备只向原生移除接口提交选定的具体实例。
6. 操作持有忙碌锁；原生调用期间禁止重复提交。不在异常后自动重试非幂等增删。成功后重新读背包，显示实际增减和数量，不仅凭“方法未抛异常”报成功。
7. 部分完成或原生结果不一致时，立即停止后续写入、保留检查点和诊断，明确提示实际已发生的变化；不承诺能用反向增删抵消剧情、词条或奖励副作用。恢复使用完整检查点。

检查点要在使用期间免于清理；复用现有读取目标保护或显式加入被保护 generation。不能因为新建备注失败而继续把不确定的检查点当作有效保护。缩略图是可选项，不影响已验证存档的保护资格。

## 战斗阶段、检查点与执行约束

- 分开实现面板可见策略、普通编辑策略和战斗策略。可以在稳定战斗中打开面板查看战斗页；不能由此开放物品、角色或点数写入，也不能放宽完整存读档安全条件。
- 不通过 `Time.timeScale = 0` 或冻结游戏协程实现安全。操作仅在已核实的原生稳定待命/输入阶段执行；进场、动画/技能处理、死亡队列、剧情对话、结算、转场、存读档与未知阶段全部禁用。
- 单靠 `_IsBattle == true` 不足以证明安全。实现阶段需将原生字段及当前行动/死亡队列的含义核实成明确状态机；无法核实就不开放写入。
- 每场战斗有自己的世代标识，结合 manager 实例、战斗开始沿和原生战斗标识，不仅使用可能重复的 `_BattleTableId`。旧单位引用、确认框、执行锁不带入新战斗。
- 使用已明确选定的完整检查点，不自动回退到另一份历史。排除无元数据的 Legacy 检查点；展示实际时间、地图、周目/等级，检查其记录早于本场战斗开始。`Store.Validate` 和 `NativeSave.Validate` 均通过才可执行。损坏/删除/目标改变则取消操作。
- 历史检查点可能来自较早进度，不能据指纹和哈希声称它与本场剧情进度相同；界面准确展示实际回退点。当前 schema 没有剧情进度谱系证明，不在首版伪造“刚开战前已自动保存”的承诺。
- 战斗过程中保护使用中的 generation 不被修剪；每次战斗按钮执行前重新验证。没有符合条件的已选检查点时给出“请在战前安全场景 F5 建立并选择检查点”的说明。
- 恢复：重新读取并筛选有效我方单位，调用已验证的恢复入口；跳过死亡/已移除单位。对数值结果逐项核对，说明因状态造成的未恢复，不把恢复当作复活。
- 击败：先核实 `EnemyHurt` / `DieEnemy` 的入口契约、参数和协程调度，选择能维护原生死亡动画、集合移除、奖励、战斗目标和剧情回调的路径。插件不独立调用 `EnemyDies/DieAward/BattleEndUI` 来拼凑结算，也不使用 `SkillCure(-1f)` 或单改 HP 代替。
- 确认后对当前存活敌人取稳定快照；正在死亡/已结算对象不能重复处理。一次操作期间屏蔽两个战斗按钮；本场“击败”提交只允许一次，失败后也不自动重试可能已发奖的对象。
- 等待原生流程完成或安全地报告超时；记录战斗世代和处理状态。超时不自行补发奖励或强行跳剧情，不让锁泄漏到下一场战斗。
- 特殊胜负条件、存活目标、分波援军、脚本敌人重生等场景，必须逐类证实支持才能开放击败；识别不充分时禁用，不能把“敌方列表暂时清空”解释成获胜。

## 性能目标与验证方法

下列是验收目标，尚无运行结果。具体场景、样本数、基线与误差要随报告保存。

- 面板关闭时不进行物品目录扫描、图标请求或背包轮询；每帧最多做常数级生命周期状态检查。
- 缓存已热的列表滚动，插件自身更新/绘制 CPU 时间以 p95 不超过 2 ms 为初始目标；搜索结果在停止输入后约 150 ms 内可交互。达不到时定位、优化并披露实测，不写“零卡顿”。
- 单帧新图标请求数和持有数受上述硬限制；记录冷加载单次最大耗时，不能用平均值掩盖少数长阻塞。
- 以同一批目录执行至少 20 轮打开/滚动/关闭，记录插件持有图标数归零、原生引用/池变化与内存趋势；不能仅凭一次 GC 或工作集下降宣称无泄漏。
- 首次操作检查点的磁盘耗时单列，后续会话内操作不能反复创建检查点；校验开销在提交时测量，不放入 `OnGUI`。

## 验证与交付

### 自动化

- 数量解析/边界、溢出、保护分类、背包实例选择、已穿戴/锁定排除、搜索索引与选择稳定性。
- 检查点失败不放行、只有完整成功才标记保护、失败可重试、关闭/读档/转场失效、重复提交被拒绝。
- 战斗阶段禁用矩阵、检查点缺失/损坏/目标变化、跨战斗旧引用、确认失效、执行中与已提交的重复请求。
- 图标请求预算、租借上限、世代失效/迟到回调清理等可与 Unity 隔离的状态逻辑。
- 既有完整测试及 Release 构建，保留实际输出；不为了通过测试放宽安全策略。

### 隔离副本真实游戏验证

- 从备份的正式快存复制到既有隔离副本，所有写入和战斗验证只落在隔离版；测试启动前按工具约束确认正式游戏状态，不擅自关闭用户正在运行的正式游戏。
- 原生图标按两种先后顺序验证：先打开游戏背包再开工具、先开工具再打开游戏背包；覆盖用户指出的 `Exiangnang` 和多类别物品，检查新日志中重复 Bundle/加载错误、两边图像及描述是否对应。
- 覆盖冷/热滚动、筛选、切页、关闭再开、换地图、读取检查点、缺失/异常资源和迟到结果；核对游戏原生背包图标继续正常。
- 普通物品增删与读档还原；多件装备实例唯一、不串词条、不删除穿戴或锁定装备；任务/信件不允许写入；数量边界和失败/部分完成报告。
- 恢复单人/全队、滞息单位、死亡单位排除；核对气血/护甲/真气与文案一致。
- 正常战斗击败：原生死亡、经验/掉落仅一次、正常离场、再次战斗与剧情回调；覆盖重复确认、阶段变化、执行超时。特殊战斗只在其类型明确通过后列入支持范围。
- 验证检查点确可通过原有完整场景读取流程还原相关状态，且原生存档位与正式存档未被测试修改。

### 完成标准

- 所有已开放功能完成相应核心测试及隔离运行验证，图标不影响游戏原生 UI，数据与回退结果可核对，性能实测随交付保存。
- 原生死亡入口契约、稳定战斗阶段或图标引用配对存在未解决问题时，不声称全部完成；继续调查或明确报告阻塞点，不能用旧危险实现兜底。
- 本次设计确认只进入实现与隔离验收；正式 DLL 部署在验收通过后提供具体构建、验证与回退记录，再依用户授权执行。不得因启动现有一键脚本而提前部署。
